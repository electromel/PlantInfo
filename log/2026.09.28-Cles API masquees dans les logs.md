# 2026.09.28 — Clés API masquées dans les logs HTTP

## Demande

La clé Gemini apparaissait en clair dans logcat (build debug) :
`okhttp.OkHttpClient: <-- 200 https://generativelanguage.googleapis.com/…:generateContent?key=AIza…`.
HttpLoggingInterceptor logge l'URL complète, et Gemini comme Pl@ntNet y passaient leur clé.

## Fait

- **Gemini** (`data/remote/ai/GeminiClient.kt`) : la clé part dans l'en-tête `x-goog-api-key`,
  plus dans `?key=`. L'URL (`ENDPOINT`) ne contient plus de secret.
- **Pl@ntNet** : l'API n'accepte la clé qu'en paramètre `api-key=`, on ne peut pas la déplacer.
  OkHttp 4.12 n'a pas de `redactQueryParams` (apparu en 5.x) : `NetworkModule` branche donc un
  `Logger` qui passe chaque ligne par `data/remote/LogRedactor` (masque `api-key`, `key`,
  `api_key`, `apikey`, `access_token` en paramètre d'URL).
- `redactHeader` sur `Authorization`, `x-api-key`, `x-goog-api-key` : sans effet au niveau BASIC
  actuel, mais protège si quelqu'un relève le niveau à HEADERS.
- Release : niveau `NONE` (déjà le cas, vérifié) — rien n'est loggé.

## Vérification

- `:app:compileDebugKotlin :app:compileReleaseKotlin :app:testDebugUnitTest` : OK.
- `LogRedactorTest` (4 tests) : clé Pl@ntNet masquée en requête et en réponse, `key=` après un
  autre paramètre, `taxonKey=` de GBIF laissé intact.
